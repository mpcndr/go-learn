# คิดเป็นระบบ แล้วเขียนออกมาเป็น Go

> "เขียนไม่ออก" ส่วนใหญ่ไม่ใช่เพราะไม่รู้ syntax แต่เพราะ **ยังคิดไม่จบ**
> ถ้าคิดจบแล้ว โค้ดจะเป็นแค่การ "แปลภาษา" จากความคิดเป็น Go

เอกสารนี้คือกระบวนการที่ใช้ได้กับทุกโจทย์ ตั้งแต่ฟังก์ชันเล็ก ๆ ไปจนถึงระบบใหญ่

---

## 1. กระบวนการ 6 ขั้น: จากหัว → โค้ด

```
 ① เข้าใจโจทย์  →  ② หาข้อมูล (นาม)  →  ③ หาพฤติกรรม (กริยา)
        ↓
 ⑥ เขียนโค้ด  ←  ⑤ เขียน test ก่อน  ←  ④ ขีดเส้นแบ่ง (boundary)
```

### ① เข้าใจโจทย์ — เขียนเป็นประโยคสั้น ๆ
เขียน 3–5 ประโยคว่า "ระบบนี้ทำอะไร ให้ใคร" ถ้าเขียนไม่ได้ แปลว่ายังไม่เข้าใจ อย่าเพิ่งเปิด editor

> ตัวอย่าง: *"สมาชิกยืมหนังสือได้ไม่เกิน 3 เล่ม หนังสือเล่มหนึ่งถูกยืมได้ทีละคน ต้องคืนภายใน 14 วัน ถ้าเกินมีค่าปรับวันละ 5 บาท"*

### ② หาข้อมูล — ขีดเส้นใต้ "คำนาม"
คำนามส่วนใหญ่จะกลายเป็น `struct`

> สมาชิก → `Member`, หนังสือ → `Book`, การยืม → `Loan`, ค่าปรับ → `Money`

ถามต่อว่าแต่ละตัว **มีข้อมูลอะไร** และ **ข้อมูลไหนเป็นตัวระบุ (ID)**

```go
type Loan struct {
    BookID   BookID
    MemberID MemberID
    DueAt    time.Time
}
```

> **Go คิดจากข้อมูลก่อนเสมอ** — ถ้าออกแบบ data ถูก โค้ดส่วนที่เหลือจะง่ายเอง
> (Rob Pike: *"Data dominates. If you've chosen the right data structures, the algorithms will almost always be self-evident."*)

### ③ หาพฤติกรรม — ขีดเส้นใต้ "คำกริยา"
คำกริยาจะกลายเป็น function / method และให้ถามทันทีว่า **"อะไรที่ผิดได้บ้าง?"** — นั่นคือ `error` ของคุณ

| กริยา | signature | ผิดได้อย่างไร |
|-------|-----------|---------------|
| ยืม | `Borrow(memberID, bookID) (Loan, error)` | ยืมเกิน 3 เล่ม, หนังสือถูกยืมอยู่, ไม่พบสมาชิก |
| คืน | `Return(bookID) (fine Money, error)` | หนังสือไม่ได้ถูกยืม |

การเขียน signature ก่อนเขียนเนื้อในคือการ "ออกแบบ" — มันบังคับให้ตัดสินใจว่า input/output/error คืออะไร

### ④ ขีดเส้นแบ่ง — อะไรคือ "ข้างใน" อะไรคือ "ข้างนอก"
แยก 3 ชั้นเสมอ:

```
┌──────────────────────────────┐
│  ขอบนอก (CLI, HTTP, DB)       │  ← เปลี่ยนบ่อย, ทดสอบยาก
├──────────────────────────────┤
│  service (use case / กฎธุรกิจ) │  ← หัวใจของระบบ
├──────────────────────────────┤
│  domain (ข้อมูล + กฎพื้นฐาน)   │  ← ไม่รู้จักโลกภายนอกเลย
└──────────────────────────────┘
   dependency ชี้ "ลง" เท่านั้น
```

ตรงรอยต่อระหว่างชั้น ให้ใช้ **interface ที่เล็กที่สุดเท่าที่ service ต้องการ** เช่น

```go
// service ต้องการแค่นี้ — ไม่สนว่าข้างหลังเป็น memory, file หรือ Postgres
type BookStore interface {
    Get(id BookID) (Book, error)
    Save(b Book) error
}
```

### ⑤ เขียน test ก่อน (หรืออย่างน้อยเขียน "ตัวอย่างการใช้งาน")
เขียน test จากประโยคในข้อ ① ตรง ๆ:

```go
t.Run("ยืมเกิน 3 เล่มไม่ได้", func(t *testing.T) { ... })
t.Run("คืนช้า 2 วัน ปรับ 10 บาท", func(t *testing.T) { ... })
```

ถ้าเขียน test ไม่ออก = ข้อ ②–④ ยังไม่ชัด ให้ย้อนกลับไป

### ⑥ เขียนโค้ด — ทีละชั้น จากในออกนอก
domain → service → storage → CLI/HTTP  รัน test ทุกครั้งที่เสร็จแต่ละชั้น

ดูกระบวนการนี้แบบเต็มได้ที่ [บท 13: capstone](../13-capstone-library)

## 2. หลักคิดที่ทำให้โค้ด Go "ดูเป็น Go"

### 2.1 ชัดเจน ดีกว่า ฉลาด (Clear is better than clever)
โค้ดถูกอ่านมากกว่าเขียน 10 เท่า เขียน `for` loop ธรรมดาดีกว่า one-liner ที่ต้องหยุดคิด

### 2.2 จัดการ error ตรงนั้นเลย และเติมบริบท
```go
book, err := store.Get(id)
if err != nil {
    return fmt.Errorf("borrow book %s: %w", id, err)   // บอกว่า "กำลังทำอะไรอยู่" ตอนพัง
}
```
เส้นทางหลัก (happy path) ชิดซ้ายเสมอ — error ให้ `return` ออกไปก่อน (early return)

### 2.3 Zero value ต้องใช้งานได้
ออกแบบ struct ให้ค่าเริ่มต้นใช้ได้เลย เช่น `var mu sync.Mutex`, `var buf bytes.Buffer` ใช้ได้ทันทีโดยไม่ต้อง `New...`

### 2.4 Interface เล็ก ๆ และประกาศฝั่ง "ผู้ใช้"
- `io.Reader` มี method เดียว แต่ใช้ได้ทั้งไฟล์ network gzip ...
- *"The bigger the interface, the weaker the abstraction."*
- **Accept interfaces, return structs** — รับ interface (ยืดหยุ่น), คืน struct จริง (ชัดเจน)

### 2.5 อย่าสร้าง abstraction ก่อนจำเป็น
เขียนแบบตรง ๆ ก่อน เมื่อเห็นซ้ำ 3 ครั้งแล้วค่อยดึงออกมา
*"A little copying is better than a little dependency."*

### 2.6 Concurrency คือเครื่องมือ ไม่ใช่เป้าหมาย
เขียนแบบ sequential ให้ถูกก่อน แล้วค่อยทำ concurrent ในจุดที่ช้าจริง
ทุก goroutine ที่เปิด **ต้องรู้ว่ามันจะจบเมื่อไหร่**

## 3. คำถามเช็คตัวเองก่อนเขียน (พิมพ์แปะไว้ข้างจอ)

1. ฟังก์ชันนี้รับอะไร คืนอะไร **พังได้แบบไหน**?
2. ข้อมูลนี้ใครเป็นเจ้าของ? ใครแก้ได้บ้าง? (→ value หรือ pointer?)
3. ถ้าต้องเปลี่ยนจาก memory เป็น database ต้องแก้กี่ไฟล์? (ควรเป็น 1)
4. ทดสอบฟังก์ชันนี้โดยไม่ต่อ network/DB ได้ไหม?
5. goroutine นี้จะหยุดเมื่อไหร่?
6. คนอื่นอ่านชื่อฟังก์ชันแล้ว เดาได้ไหมว่ามันทำอะไร โดยไม่ต้องเปิดดูข้างใน?

## 4. วิธีฝึกให้ "คิดเป็น"

- **ฝึกเขียน signature ก่อนเนื้อใน** ทุกครั้ง — แล้วให้ compiler ช่วยคิด
- **อ่านโค้ด standard library** (`go doc -src strings.Fields`) — นี่คือ Go ที่เขียนดีที่สุดที่มี
- **ทำโจทย์เดิมซ้ำ** หลังผ่านไป 1 สัปดาห์ โดยไม่ดูของเดิม แล้วเทียบกัน
- **อธิบายให้คนอื่น (หรือเป็ดยาง) ฟัง** — จุดที่อธิบายติดคือจุดที่ยังไม่เข้าใจ
